## #1 2026-10-15: Desktop app, not web app
**Context:** Web app would need uploads to a server or in-browser rendering.
**Decision:** Electron desktop app, everything local.
**Why:** Video files are large; local disk + local encoding is faster and free. Same codebase builds for Windows.
**Revisit if:** We need non-technical team members on other machines, or rendering moves to the cloud.

## #2 2026-10-15: Remotion for preview + render
**Context:** Options were Remotion (React compositions) or a pure FFmpeg filtergraph renderer.
**Decision:** Remotion, with `@remotion/player` for preview and `@remotion/renderer` in the Electron main process.
**Why:** One React component for both preview and export means what you see is what you get; captions are just CSS. Remotion has an official Electron template and docs for packaged rendering.
**Revisit if:** Step 0.4 spike fails, renders are too slow for batch mode, or the team grows to 4+ people involved (license cost).

## #3 2026-10-15: Normalize every clip on import
**Context:** UGC arrives as HDR HEVC, rotated, VFR, horizontal, 60 fps.
**Decision:** Transcode every import to SDR H.264, 30 fps CFR, rotation baked, long edge max 1920.
**Why:** One predictable input format removes a whole class of washed-out color, sync, and seeking bugs, and makes preview fast.
**Revisit if:** Import time becomes a bottleneck (consider hardware encoding).

## #4 2026-10-15: Recipe JSON as the single source of truth
**Context:** Need reopen/edit, batch, and future sharing.
**Decision:** Every video is a versioned, zod-validated Recipe; exports write a `.recipe.json` sidecar.
**Why:** Re-rendering and editing old videos is free; batch mode is just generating many recipes.
**Revisit if:** Never, really. Bump `schemaVersion` and migrate when the shape changes.

## #5 2026-10-15: Local SQLite now, Supabase for sharing later
**Context:** Two users on separate Macs.
**Decision:** v1 is single-machine SQLite in a user-chosen library folder. Sharing (Phase 5) uses Supabase for metadata and a shared drive for media only.
**Why:** SQLite files corrupt in Dropbox/Drive sync. Metadata is tiny; media is huge. Split them.
**Revisit if:** Sharing becomes urgent before Phase 5.

## #6 2026-10-15: Map our folder layout onto the Remotion Electron template
**Context:** The official template (remotion-dev/template-electron) is flat: `src/main.ts`, `src/preload.ts`, `src/renderer.ts`, `src/App.tsx`, plus `src/render-video.ts` and friends. `CLAUDE.md` wants `src/{main,preload,renderer,shared}`.
**Decision:** Keep the template's tooling and config files at the repo root (`forge.config.ts`, `vite.*.config.ts`, `index.html`, `remotion/`) and move only the source files:
- `src/main.ts` → `src/main/main.ts`
- `src/preload.ts` → `src/preload/preload.ts`
- `src/renderer.ts`, `src/App.tsx`, `src/index.css` → `src/renderer/`
- `src/render-video.ts`, `remotion-bundle.ts`, `packaged-browser.ts`, `compositor-package.ts` → `src/main/render/`
- `src/integration-render-test-mode.ts` → `src/main/`
- IPC channel names and the `SandwichApi` type → `src/shared/ipc.ts`
The only config changes are the entry paths in `forge.config.ts` and the script path in `index.html`. Entry files keep the basenames `main.ts` and `preload.ts` because the Forge Vite plugin names its output after the entry file, and `package.json#main` points at `.vite/build/main.js`.
**Why:** Matches the documented layout without touching the packaging logic the template already solves.
**Revisit if:** A template upgrade moves files again.

## #8 2026-10-15: FFmpeg + FFprobe from ffmpeg-static's pinned GitHub release
**Context:** Need ffmpeg and ffprobe for macOS arm64 + x64 now and Windows x64 later, with zscale/tonemap for HDR, libx264, and the filters normalization needs. Options compared:
- `ffmpeg-static` npm: ffmpeg only (no ffprobe), downloads only for the host at install time.
- `ffprobe-static` npm: ffprobe 4.0.2 from 2022, Intel-only on macOS. Rejected.
- FFmpeg inside Remotion's compositor package (n7.1): already shipped and unpacked, has zscale/tonemap/libx264/libx265, but built with `--disable-filters` and a whitelist that lacks `format`, `fps`, `transpose` (needed for autorotate), `tile`, `crop`, `pad`, `overlay`, `testsrc`. Also an internal Remotion artifact with a macOS 15 minimum. Rejected.
- Pinned download script against the `ffmpeg-static` GitHub release `b6.1.1`, which publishes both ffmpeg and ffprobe for every target. Chosen.
**Decision:** `scripts/ffmpeg-fetch.ts` downloads `ffmpeg-<target>.gz` and `ffprobe-<target>.gz` from release `b6.1.1`, gunzips, verifies SHA-256 of the decompressed binary against hashes pinned in `scripts/ffmpeg/fetch.ts`, and writes them to `vendor/ffmpeg/<target>/` (gitignored). If the file already exists and its hash matches, the download is skipped; a corrupted or wrong file is re-downloaded. Runs on `postinstall` for the host (warns and skips on unsupported hosts) and from the Forge `packageAfterCopy` hook for the target arch, which stages it into `ffmpeg-bin/<target>/` and adds that folder to `asar.unpackDir`.
Builds verified with `npm run ffmpeg:check`:
- darwin-arm64: FFmpeg 6.0 (osxexperts), all required filters/encoders present, h264_videotoolbox present, no libplacebo.
- darwin-x64: FFmpeg 6.1.1 (evermeet), same capability set (checked under Rosetta).
- win32-x64: 6.1.1 essentials (gyan.dev). Not run yet; `ffmpeg:check` on Windows in Step 5.1.
Hashes were recorded from the first download (trust on first use); the release publishes no checksums.
Licensing: these are GPL builds. Fine for internal use, revisit before distributing commercially (see CLAUDE.md).
Size: about 91 MB per arm64 install (ffmpeg + ffprobe), about 158 MB for x64.
**Why:** One source for both tools, every target we need, any target fetchable on any machine (so an arm64 Mac can package x64), and integrity checked.
**Revisit if:** We need a newer FFmpeg (bump the tag and hashes together), app size matters, or a target build loses a required capability.

## #9 2026-10-15: Required FFmpeg capabilities are enforced, not just logged
**Context:** A missing filter would only surface mid-import as a cryptic ffmpeg error.
**Decision:** `npm run ffmpeg:check` exits nonzero unless these exist: filters zscale, tonemap, scale, fps, transpose, crop, pad, tile, format; encoders libx264, aac. h264_videotoolbox, libplacebo and colorspace are reported as optional. ## #10 2026-10-15: Probe parsing conventions
**Context:** ffprobe output differs across versions and devices.
**Decision:**
- `rotation` is the clockwise angle needed to display upright, normalized to 0/90/180/270. ffprobe's display matrix `rotation` is counter-clockwise (iPhone portrait reports `-90`), so it is negated; the legacy `rotate` tag is already clockwise. The display matrix wins when both exist.
- `isVfr` is true when `avg_frame_rate` and `r_frame_rate` differ by more than 1%. An exact comparison would flag nearly every phone clip.
- `recordedAt` prefers `com.apple.quicktime.creationdate` (capture time with local offset) over `creation_time` (can be export time), checking format tags before stream tags. 1904/1970 epoch placeholders count as missing. Stored as ISO 8601 UTC.
- ffprobe JSON is validated with a loose zod schema before parsing.
- `duration` is the video stream's duration (container duration only as a fallback): the container can be slightly longer because of AAC priming. `audioChannels` / `audioSampleRate` come from the first audio stream (added in step 0.3 for the fixture assertions).
- Real iPhone sample (`tests/fixtures/probe/iphone_hlg_portrait.json`, 2026-10-15): portrait stored natively as 1080x1920 with no display matrix, HEVC Main 10 HLG with a Dolby Vision configuration record, 60 fps, and a second audio stream (Apple spatial audio, `apac`) that FFmpeg 6.0 cannot decode. Location, make, model, software and encoder tags were removed and dates replaced before committing. The -90 display matrix path is covered by unit tests, not a real clip, because this phone did not write one.
**Why:** Predictable values for normalization (Step 1.2) and date-based pairing (Step 4.2).
**Note for Step 1.2:** map the AAC audio stream explicitly (not "first audio stream" blindly) so the undecodable spatial audio track is never picked.
**Revisit if:** Real Android or screen-recording clips break these assumptions, or an older iPhone clip with a rotation matrix turns up (add it as a fixture).

## #13 2026-10-15: Fixture generator conventions
**Context:** Step 0.3 needs deterministic test media that is quick to regenerate and easy to verify by eye and ear.
**Decision:**
- Every fixture has a burned-in label, running time and frame number, a "TOP" marker, a pure red 24 px bar along the top edge of the upright frame, and a sync pulse: a 0.1 s beep once per second with a full-width white flash (below the red bar) in the same window. One tone frequency per fixture.
- Caching: `fixtures/.manifest.json` (gitignored) stores a sha256 of each fixture's ffmpeg argument arrays, the ffmpeg version line, the font file hash and `GENERATOR_VERSION`. Only relative paths go into the hash. Files are written as `<name>.tmp.<ext>` and renamed on success, and a fixture is cached only if the hash matches and the file is non-empty. `npm run fixtures -- --force` rebuilds everything.
- Rotation fixture: upright content is `transpose=1`'d to 1920x1080 landscape pixels and remuxed with `-display_rotation 90`, matching `tests/fixtures/probe/rotated_ccw90.json` (ffprobe rotation 90 counter-clockwise, our `rotation: 270`, display 1080x1920). It is verified by decoding with autorotate and checking that the top 20 px strip is red, so a wrong sign fails. The more common older-iPhone sign (-90, our `rotation: 90`) is not generated yet.
- HDR fixtures (HLG and PQ, bt2020, 10-bit HEVC) are required: the generator fails if libx265 is missing. Pixel values are an SDR test pattern, so they test tagging and tone-map plumbing, not tone-map quality (that stays a real-clip human check).
- `sample.recipe.json` only uses normalized-looking clips (1080x1920, 30 fps CFR, SDR H.264). The 60 fps, VFR, 4K, rotated, mono, no-audio and HDR files are normalization and edge-case inputs. A separate edge-case recipe (no-audio clip etc.) arrives in step 1.5. The recipe uses a local type until `src/shared/recipe.ts` exists in step 1.1, where it should be validated against the zod schema.
**Why:** Flash and beep make trims and A/V sync obvious on playback; hashing avoids pointless 10 s regenerations while still noticing any change.
**Revisit if:** Fixtures become slow to generate, or Phase 1 needs more edge cases (add them to `FIXTURES`, bump nothing else).

## #15 2026-10-15: Package the headless browser by default
**Context:** The template packages Chrome Headless Shell only when `REMOTION_ELECTRON_PACKAGE_BROWSER=true`; otherwise the first render downloads it at runtime.
**Decision:** `forge.config.ts` now packages it unless `REMOTION_ELECTRON_PACKAGE_BROWSER=false`. This matches golden rule 7 (the browser lives in `app.asar.unpacked`).

## #16 2026-10-15: Remotion API choices from the 0.4 spike
- `OffthreadVideo` trim: use `trimBefore` (frames). In 4.0.535 `startFrom` and `endAt` are deprecated aliases, and `trimAfter` is deprecated in favour of `durationInFrames`; clip length is bounded by the surrounding `<Sequence>`.
- Fonts: `@remotion/fonts` (pinned 4.0.535) `loadFont({ family, url: staticFile(...) })` held with `useDelayRender`. `staticFile` resolves against `publicDir`, which we set to `assets/` for `bundle()` and `Config.setPublicDir("assets")` (Studio). One font file serves ffmpeg drawtext fixtures and the composition.
- Hardware encoding option is `hardwareAcceleration` (`disable | if-possible | required`); spike results use `required` so a silent fallback cannot be mistaken for hardware (#14).
- Encoder choice is read from Remotion's verbose log (`logLevel: "verbose"`, console tap) because `renderMedia` does not return it; the file is cross-checked via the x264 SEI string.
- Main-process runs for scripted measurement: `electron . --integration-render-test <abs .mp4> --spike-mode sw|hw|sw-bitrate|hw-if-possible` (dev, after a `forge start` build) or `open -n -W --stdout f --stderr f -a Sandwich.app --args ...` (packaged). `electron-forge start` exits immediately without a TTY, so dev measurement runs the built `.vite/build/main.js` directly.

## #18 2026-10-16: Recipe schema details (step 1.1)
- **Empty slots parse.** A draft recipe has slots with no media yet. A clip with `mediaPath === ""` skips the `trimStart + duration <= sourceDuration` check (only `mediaPath` decides this); it still needs `duration > 0`. `isRenderable` is the render gate: all three `mediaPath`s non-empty. Shape validity is `RecipeSchema`'s job, render readiness is `isRenderable`'s.
- **Clip order is in the type.** `clips` is a `z.tuple` of three slot-literal clip schemas (before, after, broll), not a refinement, so TypeScript and zod agree.
- **Float slack.** The trim check allows 1e-6 s so values like `0.1 + 0.2` at the end of a source do not fail.
- **Purity.** `createEmptyRecipe` takes `{ id, now }` from the caller (`crypto.randomUUID()`, `new Date()`) so `src/shared` stays free of Node and DOM imports and tests are deterministic.
- **Naming.** TypeScript shapes use camelCase (`productId`, `useCount`, `fullName`, `shortName`) even where SPEC tables show DB-style snake_case; the DB layer (step 2.1) maps columns.
- **Tokens** match case-insensitively (`{Product}` works); unknown tokens stay as typed and are reported with braces, once each.

## #19 2026-10-16: Export hook skips single-letter words
**Context:** SPEC section 6 said the hook is "the first 4 words" of the before caption, but its own example (`I can't fix my smile lines, it's genetics` -> `cant-fix-my-smile`) drops the leading "I"; literal first-4-words would give `i-cant-fix-my`.
**Decision:** Before taking 4 words, skip single-letter words ("I", "a") and words with no letters or digits (emoji-only or symbol-only). Single digits are kept, so "3 weeks into using this" gives `3-weeks-into-using`. Then slugify the 4 words joined by dashes, hard-cap at 30 chars (mid-word is fine), strip a trailing dash. Empty result -> `no-caption`. SPEC section 6 updated; the SPEC example is a literal test.
**Revisit if:** Real captions produce unhelpful hooks (e.g. captions made only of short words collapse to `no-caption`).

## #22 2026-10-16: Import normalization details (step 1.2)
- **Filter order.** `fps=30` first, then `scale=W:H`, then the tone map (HDR) or the range/matrix `scale` (SDR). A 60 fps source only pays for half the frames in everything after the first filter, and the tone map runs at output resolution. Rotation is left to ffmpeg's autorotate (verified: the rotated fixture comes out upright, rotation 0, red bar on top).
- **Even sizes.** `targetSize` rounds both edges to even numbers (1206x2622 -> 884x1920) and never upscales. The output may therefore differ from the exact aspect ratio by up to 1 px; `normalizeCheck` allows 1 px.
- **Audio stream choice.** Real iPhone clips carry two audio streams: AAC stereo plus Apple `apac` spatial audio (4 ch) that ffmpeg cannot decode, and six `mebx` data tracks. `ProbeResult.audioStreamIndex` is the absolute index of the first audio stream with a recognised `codec_name`; `hasAudio`, channels and sample rate come from that stream. `buildNormalizeArgs` always maps `0:v:0` and `0:<audioStreamIndex>` explicitly, plus `-map_chapters -1 -map_metadata -1`. No decodable audio means a `anullsrc` stereo 48 kHz input is mapped instead.
- **Audio sync.** `aresample=async=1:first_pts=0,apad` with output `-t <source duration>`: audio starts at 0, is padded with silence if short, and cut if long. All 15 clips end with audio within one frame of video.
- **SDR range and matrix are inputs, not assumptions.** The SDR `scale` sets `in_range` from `colorRange` (`pc` -> full) and `in_color_matrix` from `colorSpace` (`smpte170m`/`bt470bg` -> bt601, everything else including untagged -> bt709), then outputs tv range and bt709. This matters: the real screen recording is full-range `yuvj420p`.
- **`ProbeResult` grew** `audioStreamIndex`, `audioCodec`, `audioDuration`, `colorSpace`, `colorPrimaries`, `colorRange`.
- **Output written to `<out>.partial`** and renamed on success. On failure or abort the partial is deleted only after the ffmpeg child has emitted `close` (Windows holds file locks until then).
- **Not changed on purpose:** no `-g` / keyframe interval override yet. Revisit in 1.4 if scrubbing in the Player is slow (default x264 GOP is up to 250 frames, about 8 s at 30 fps).

## #23 2026-10-16: HDR tone mapping is zscale-only (deviation from BUILD_PROMPTS 1.2)
BUILD_PROMPTS step 1.2 and ARCHITECTURE section 6 say to fall back to `libplacebo` or `colorspace` when `zscale` is missing. We do not. `zscale` is a REQUIRED filter in `capabilitiesParse.ts`, so a build without it already fails `npm run ffmpeg:check` and the startup capability check; a fallback could never run. `libplacebo` also needs a Vulkan device (absent in the pinned build and unreliable on headless machines), and `colorspace` cannot read HLG or PQ transfers. `chooseToneMapPath` therefore returns `"zscale"` or throws a clear error, and `NormalizeResult.toneMapPath` is `"zscale" | null`.
**Revisit if:** the pinned FFmpeg build changes and loses `zscale`.

## #24 2026-10-16: Tone map evaluation method and results (step 1.2)
**Method.** Comparing HDR playback to an SDR file on an EDR display is not fair (the original always looks brighter), and mean luma of HLG code values versus SDR code values means nothing. The reference is Apple's own conversion of the same clip: `avconvert -s fixtures/real/iphone_hdr.MOV -o out/normalized/iphone_hdr_apple_sdr.mov -p Preset1920x1080` (confirmed bt709 / tv / yuv420p / h264, 1080x1920). `npm run normalize -- <hdr clip> <out.mp4> --tonemap-variants` writes the variants and prints mean Y and R/G/B (6 sampled frames, 360x640 decode) and SSIM against that reference, plus a side-by-side PNG.
**Results (iphone_hdr.MOV, HLG):**

| variant | meanY | meanR | meanG | meanB | SSIM vs Apple |
|---|---|---|---|---|---|
| Apple reference | 125.2 | 131.8 | 123.9 | 117.6 | 1.0000 |
| hable, npl 100 (doc default) | 142.9 | 151.4 | 141.4 | 133.4 | 0.9795 |

## #25 2026-10-16: Media server design (step 1.3)
**Decision:**
- URL shape `http://127.0.0.1:<port>/m/<token>/<seg>/<seg>`; the token is 24 random bytes (base64url) per app session. The base URL contains the token, so it is never logged or emitted (only the port is). `library.mediaBaseUrl()` returns it over IPC; `mediaUrl(base, relPath)` builds file URLs and encodes each segment.
- Path parsing is segment-wise: the raw request target (`req.url`, not a WHATWG URL, which collapses `..` and `%2e%2e`) is split on `/` first, then each segment is decoded once. Empty, `.`, `..`, or segments containing `\`, NUL, `:` or a decoded `/` get 403 (`:` blocks Windows drive letters and NTFS alternate data streams); malformed percent-encoding gets 400. Pure string logic in `src/shared/mediaPath.ts`.
- Filesystem containment is in main (`src/main/media/pathGuard.ts`, because it uses `node:path`): both the root and the target are `realpath`'d before comparing, so symlinks cannot escape and a root reached through a symlink (macOS `/var` -> `/private/var`) still works. On win32 the comparison is case-insensitive (`path.win32.relative`).
- `startMediaServer({ getRoot })` takes a function, not a path. A null or unresolvable root returns 503, never a crash, so step 2.1 only changes what `getRoot` returns (no restart). Today: `fixtures/` in dev, `null` in packaged builds.
- The spike keeps its own server instance (root = the spike media dir) so `--integration-render-test` still works without a window. The app-wide server and the spike's are the same module. The spike's old server and path guard are deleted (this part of the 1.4 cleanup item is done).
- Token compare uses SHA-256 digests with `timingSafeEqual` (no throw on unequal lengths). Bodies use `stream.pipeline` so aborted scrub requests release the file descriptor.
- CORS `Access-Control-Allow-Origin: *` with exposed `Content-Range`, `Accept-Ranges`, `Content-Length`, plus OPTIONS 204 for preflight. Remotion's headless browser and the Electron renderer both load cross-origin; the token, not the origin, is the access control. Other methods get 405 with `Allow`.
- Caching: `Cache-Control: private, max-age=3600` with `ETag` (size + mtime) and `Last-Modified`, and 304 on a matching `If-None-Match` (not for range requests), so a file replaced at the same path is not served stale.
- CSP (`index.html`): added `media-src 'self' http://127.0.0.1:* blob:` and `http://127.0.0.1:*` to `img-src`. `connect-src` already allowed it.
**Revisit if:** the library root can change at runtime (cached entries for the old root), or we need auth beyond a per-session token.

## #26 2026-10-16: SandwichVideo composition design (step 1.4)
**Decision:**
- **Props and metadata.** `SandwichProps = { recipe, mediaBaseUrl, showSafeZone?, showTimecode? }` (`remotion/types.ts`). `calculateMetadata` runs `RecipeSchema.parse` and returns the parsed recipe in `props`, so the component only sees validated data; `durationInFrames` is the sum of the timeline's clip frames; width, height and fps come from `recipe.output`. `defaultProps` is an empty recipe with a fixed uuid and `new Date(0)`, so the prebuilt bundle is deterministic and never imports `fixtures/` (gitignored). Studio gets the real recipe through `--props` (`scripts/studio.ts`).
- **Frame math** (`src/shared/timeline.ts`): clip boundaries are `round(cumulativeSeconds * fps)` and clip lengths are the differences, so rounding never accumulates. The 1-frame minimum per clip wins over exact rounding; the total is always the sum of the clip frames, and equals `round(totalDuration * fps)` whenever no clip hits the floor (a later boundary usually re-absorbs a floored clip). `trimBeforeFrames = min(round(trimStart*fps), max(0, floor(sourceDuration*fps) - durationInFrames))`, so the clip window never reads past the source. Empty slots keep their duration, trim 0, and render black.
- **Zoom** (`src/shared/zoom.ts`, no `remotion` import): `slow-push` 1.0 to 1.12 over `d-1` frames (last frame exactly 1.12) with cubic ease in-out; `punch-in` 1.0 to 1.25 over `round(0.25*fps)` frames with cubic ease-out, then hold. `transform-origin` and `object-position` both come from `focus`. The caption sits outside the zoom wrapper, so text never scales.
- **Caption layout** (`src/shared/captionLayout.ts`): greedy wrap honouring `\n` at 80% of the safe width (minus stroke or box padding reserve), max 3 lines, font 64 px down to a 36 px floor in 2 px steps. **Overflow rule:** if it still does not fit at the floor, keep the floor size, draw every line (never truncate user text), keep the block inside the safe rect, and return `overflow: true` (phase 3 editor warns). A word wider than a line is hard-broken by character. `top` centers the block in the upper third of the safe rect, `middle` centers it in the rect. Also in SPEC section 7.
- **Font readiness.** `remotion/fonts.ts` keeps one module-level `loadFont` promise (a Player remount never adds a duplicate FontFace) and exports `useFontReady()` (holds a `delayRender` handle, returns a boolean). `Caption` lays out only when the flag is true and keys its memo on it, so the first layout never uses fallback metrics. `measureText.ts` measures with exactly the CSS shorthand used for drawing (weight 700, same family string, px size, `letterSpacing: 0px`) and never caches a measurement taken before `document.fonts.check` passes. Reuses TikTok Sans 36pt Bold (#12); no new font. **Known 3.2 follow-up:** `staticFile()` in the Electron-renderer Player must resolve this font file.

A first try at 0.22 em closed the word gaps in the real frames, so it was thinned. `box`: one rounded white rect per line, hugging that line's width, black text, rects stacked with no gap.
- **Video component: `OffthreadVideo`, not `<Video>` from `@remotion/media`.** Remotion's docs now recommend `@remotion/media`. We keep `OffthreadVideo` because it is proven in the packaged render (#14), is frame-accurate, needs no new dependency, and in the Player/Studio it falls back to an HTML5 video (confirmed in 4.0.535 source), so one component tree serves preview and render. **Revisit in 3.2** if Player scrub accuracy or speed is poor.

- **Debug overlays** `showSafeZone` and `showTimecode` default to false; they are on in `npm run studio` and `npm run frames` only.
- **Studio script.** `scripts/studio.ts` spawns `process.execPath` with the resolved `@remotion/cli/remotion-cli.js` (not `.bin/remotion`, which is a `.cmd` on Windows), forwards SIGINT/SIGTERM, and closes the media server when the child exits. The props file `out/studio-props.json` holds the session token (`out/` is gitignored); the base URL is never printed (#25).

Packaged rendering of the new composition is not exercised in 1.4; 1.5 and the Phase 1 exit test re-prove it. A packaged build (browser skipped) was made and its prebuilt bundle contains `Sandwich` and no spike code.

## #28 2026-10-17: Library folder and SQLite (step 2.1)
**Decision:**
- **better-sqlite3 13.0.3 (exact pin) needs no Electron rebuild.** Its package ships N-API prebuilds (`prebuilds/<platform>-<arch>.node`, darwin/win32/linux), has `"gypfile": false` and no `install` script, and `lib/binding.js` loads `../prebuilds/<platform>-<arch>.node`. N-API is ABI-stable, so one binary serves Node 22 (Vitest) and Electron 40. Proof on this Mac: `npm install` created no `build/` directory; `ELECTRON_RUN_AS_NODE=1 npx electron -e "..."` printed `{ v: '3.53.4' } 40.10.2`, plain Node 22 printed `{ v: '3.53.4' }`. Packaging: `better-sqlite3` is external in `vite.main.config.ts` (the Forge Vite plugin leaves `node_modules` out of the app), `forge.config.ts` stages `package.json`, `lib/` and only the target's prebuild into `node_modules/better-sqlite3/`, and `node_modules/better-sqlite3/prebuilds` is in `asar.unpackDir` (golden rule 7). Verified packaged: `Sandwich --db-check <dir>` printed `packaged: true`, SQLite 3.53.4, WAL, foreign keys on, schema version 1. `@types/better-sqlite3` is 9.6.0 (v13 ships no types).
- **Dev uses its own userData.** Unpackaged runs set `userData` to `Sandwich-dev` (sibling of `Sandwich`) before `app.ready`, so a dev build with newer migrations can never open or migrate the real library that the packaged app uses (the packaged app would then refuse it as "schema newer than app"). `SANDWICH_USER_DATA` overrides both. Cost: dev and packaged no longer share a library; to test the packaged app on real data, point it at a copy.
- **Settings and the two-phase switch.** `<userData>/settings.json` (`{ libraryPath }`, zod-validated, atomic write; missing or corrupt reads as unconfigured). `library.choose()` inspects a folder and main remembers it; `library.activate()` opens exactly that remembered folder, so the renderer never sends a path to main. The new library is opened before the old one is closed, so a failed switch leaves the current library active. A saved library whose folder or `library.db` is missing is an `error` state (setting kept, nothing silently created); it can be a disconnected drive.
- **Default path** is `path.join(app.getPath("videos"), "SandwichLibrary")` (`~/Movies/SandwichLibrary` on macOS).
- **Folder inspection.** Sync detection (`src/shared/syncedFolders.ts`) is a path-segment heuristic run on the `realpath` (a symlink into Dropbox is caught); it warns and never blocks, and cannot see a synced Desktop or Documents. A non-empty folder that is not a library gets a `SandwichLibrary` subfolder proposed as the default (the picked folder can still be used directly); the default path itself is never nested. `schemaTooNew` is found by opening `library.db` read-only and comparing `MAX(version)`, before Confirm, with no migration or backup.
- **Pragmas and shutdown.** `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`, `busy_timeout=5000`. Closing runs `wal_checkpoint(TRUNCATE)` first so `library.db` is self-contained.
- **Migration safety.** Migrations are `src/main/db/migrations/NNN_name.sql`, bundled with `import.meta.glob(..., { query: "?raw" })` (works in Vite, Vitest and the asar). Each runs in its own transaction and is recorded in `schema_migrations`. Before applying pending migrations to an existing non-empty database, `db.backup()` writes `library.db.bak-v<oldVersion>` (newest 3 kept; a failed backup aborts). `PRAGMA foreign_key_check` must be empty afterwards or `ForeignKeyViolationError` is thrown. A database newer than the app throws `SchemaTooNewError`.
- **Future table-rebuild migrations.** SQLite cannot alter most constraints in place, so such a migration creates a new table, copies, drops the old one and renames the new one (in that order: renaming the old table first rewrites the children's references to it; a test pins this). That needs `PRAGMA foreign_keys=OFF`, which is a no-op inside a transaction. The runner supports it: a leading comment `-- sandwich: foreign_keys=off` makes it set the pragma before `BEGIN`, run `foreign_key_check` before `COMMIT` (a bad rebuild rolls back), and turn the pragma back on. Unused in 001.
- **Products are archived, not deleted.** `products.archived_at` (new column in 001, extends ARCHITECTURE section 4, doc updated) hides a product from `products.list` and pickers by default while its videos and history stay. Hard delete only works with zero videos and otherwise throws `ProductHasVideosError` (the 2.3 UI will offer "Archive instead"). `videos.product_id` keeps no cascade, as in ARCHITECTURE. Deleting files under `products/<id>/` is the service layer's job (2.3), not the repository's.
- **One traversal rule.** `isSafePathSegment` in `src/shared/mediaPath.ts` is used by both the media server and `assertRelativeLibraryPath` (repositories, `toAbsolute`), and a test checks they reject the same hostile segments. The media server still resolves with `pathGuard.ts` only. `getRoot` is read per request, so switching libraries re-roots it; with no library it returns 503. The dev `fixtures/` fallback is removed (nothing used it: `npm run render:sample` and `npm run studio` run their own servers). A test with two real libraries confirms the same relative path serves different bytes after a switch and a path only in the old library gives 404.
- **Packaged check without UI.** `Sandwich --db-check <abs dir>` (`src/main/library/db-check-test-mode.ts`, like `--render-recipe` in #27) opens a library, round-trips a row, writes `db-check.result.json` and exits.
**For step 5.1 (Windows):** the Windows `Videos` known folder is often redirected into OneDrive, so `app.getPath("videos")` can land in a synced folder and trigger the sync warning by default. Revisit the default library path there.
**Revisit if:** a library must be shared across machines, or the renderer caches media URLs across a library switch (the ETag plus `private, max-age=3600` headers are keyed by URL, so a long-lived `<video>` element could show stale bytes until reloaded; nothing caches today).

## #29 2026-10-17: Job queue and importClip (step 2.2)

- **The scheduler is pure and closure based.** `src/shared/jobScheduler.ts` takes `enqueue({ type, label, run })`; the runner is a closure, so a job captures the library `root` and `repos` it was started in and tests use fake runners. Limits: `importClip` 2, `render` 1, separate pools, FIFO. Only types with a runner are defined: `importClip` now, `render` is typed with its limit but rejects with "not available yet" until 3.5. Standalone `thumbnail` and `filmstrip` types from ARCHITECTURE are dropped until something needs them; they are stages inside `importClip`.
- **`importClip` holds one slot for its whole run** (normalize 0-90%, thumbnail 90-95%, filmstrip 95-100%), so 6 imports run 2 at a time. The thumbnail and filmstrip stages are seconds long and would only add queue plumbing as separate jobs.
- **`cancelling` keeps the pool slot** until the runner settles, so a cancel can never let a third ffmpeg start; `cancelAll()` resolves only after every runner has settled (every child has closed). An abort (or any error after a cancel request) is `cancelled`, not `failed`; a runner that finishes anyway is `done`.
- **No staged copy of the original (differs from BUILD_PROMPTS 2.2, "copy file into the library").** ffmpeg opens the original read-only and nothing is written to it (golden rule 6 holds), and multi-GB 4K HDR clips are not copied before they are converted anyway. The library only ever holds the normalized file. `original_name` stores the original basename. Cost: a source that is moved or unplugged mid-import fails that job.
- **Outputs are built in `cache/tmp/<jobId>/` and renamed into place; the row is inserted last.** `signal.aborted` is checked before the renames (same volume, cheap). A crash anywhere before that leaves only `cache/tmp`, which `sweepLibrary` empties. Remaining gap: a crash between the renames and the insert leaves three orphan files and no row (a few microseconds wide; the files are harmless and no row points at them). `repos.media.create` takes an optional `id` because the file names are built from it before the insert.
- **Clip folder month is the local import date** from the injected clock (`clips/<yyyy-mm>/<clipId>.mp4`), not the recorded date.
- **`sweepLibrary(root)` is separate from `openLibrary()`.** `--db-check` and the scripts also call `openLibrary`, and must not wipe staging a running app is using. `libraryManager` runs it on init and after a switch (once the old library's jobs are cancelled); `scripts/test-import.ts` calls it explicitly.
- **Library switch:** `libraryManager.activate` opens the new library, saves the setting, then awaits `beforeClosePrevious` (main passes `cancelAll`), then closes the old database. A failed switch cancels nothing.
- **Quit:** `will-quit` is synchronous, so `before-quit` (once, guarded) prevents the quit while jobs are active, awaits `cancelAll`, then calls `app.quit()` again; `will-quit` only closes the media server and the database.
- **One event channel, `job:event`,** replaces the three channels in the first ARCHITECTURE draft: `queued`, `started`, `progress`, `done`, `failed`, `cancelled`, each carrying a full `JobInfo` with a scheduler-wide `seq`. The renderer subscribes first, then loads `jobs.list()`, and keeps the higher `seq` per job, so a stale snapshot cannot undo a newer event (cancelled jobs stay in the store, hidden, for the same reason). Progress is throttled to about 10 per second per job in main; state changes are never dropped, and a pending progress is discarded when a state change for that job goes out. Sends are guarded for a closed window (macOS keeps jobs running).
- **`run.ts`:** `runCapture` now takes a `signal`, and its timeout path SIGKILLs and waits for `close` before rejecting, like abort and `runStreaming`, so callers can delete files afterwards (Windows would refuse otherwise). Thumbnails and filmstrips are cancelable.
- **Dev tooling:** the "Dev: import all fixtures" button in the tray exists only when `import.meta.env.DEV`; its main-side handler is registered only when the app is not packaged and picks the files itself (the renderer sends no path). `npm run test:import` runs the same flow headless with real ffmpeg (it reads the SQL migrations directly because `import.meta.glob` does not run under tsx).

- **Settings live in `<userData>/settings.json`** (per machine), not in SQLite. WHERE status = 'draft'` (`videos.upsertDraft`): it keeps `created_at` and `product_id`, and never overwrites a video that is not a draft (`{ ok: false, code: "not-draft" }`). On launch (and after a library switch) the editor opens it only if the row still exists and is still a draft; otherwise the pointer is dropped and New Video shows the product grid. The real guarantee is "every action whose save has resolved is on disk"; the loss window is a quit during an in-flight save. A failed save shows "Could not save the draft" in the editor.
- **Library switch.** `libraryStore.activate` first awaits the editor's pending saves (they land in the OLD library) and sets `switching`, which blocks new saves and imports. On success the editor resets (pending imports, missing flags, draft), bumps `epoch` and hydrates from the new library; on failure `switching` is cleared and editing continues. Every queued save, import and job result carries the epoch it started in and is dropped if it changed, so library A's draft can never be written into library B.
- **Slot import is race-safe.** `jobId -> slot` lives in the store (`pending`). After `media.importUgc` resolves the job is recorded, then checked against the jobs store in case it already finished (or failed or was cancelled) before it was mapped. On `done` the media row is fetched with `media.get`, and the result is applied only if the epoch and the draft id are unchanged AND `pending[slot].jobId` is still that job; otherwise it is dropped. A slot is "Clip missing" when either is false, which covers deleted b-roll (DECISIONS #31) and files removed by hand. The recipe keeps its `mediaPath`, so nothing crashes and Replace fixes it.

- **IPC additions:** `settings.get/update/getOpenDraft/setOpenDraft`, `videos.saveDraft/list/get/remove` (`remove` is drafts-only), `media.get/byPaths`. User-fixable failures are `{ ok: false, code, message }` like the other domains.

## #35 2026-10-17: Trim panel (step 3.3)

- **Bounds come from the recipe.** All trim math uses `clip.sourceDuration`, not the Media row, so the window can never be something the export would reject. `src/shared/trimMath.ts` is pure: `snap` (0.1 s, microsecond-rounded so `0.1 + 0.2` noise never reaches the recipe), `clampTrim`, `moveWindow`, `resizeStart`, `resizeEnd`, `setStart`, `setDuration`, `resetLength`, `nudge*`. Minimum window is 0.5 s, or the whole clip when the clip is shorter.
- **Drags are computed from the gesture origin.** `Filmstrip` stores the origin trim and origin pointer x on pointerdown; every move calls `moveWindow` / `resizeStart` / `resizeEnd` with the TOTAL travel. Adding each small move to the current trim would let snapping swallow slow drags (tested: 100 moves of 0.01 s end 1.0 s away). Escape mid-drag restores the origin trim and ends the gesture without saving.
- **Edge semantics.** The left handle keeps the END where it was (start and length change); the right handle keeps the start. `setDuration` keeps the start unless that overflows, then the start moves earlier so the typed length is honored (capped at the clip length). "Reset to default length" (`resetLength`) keeps the start, sets length to `min(slot default, source)` and moves the start earlier only on overflow; the button is disabled when already there.
- **Off-grid sources** (8.37 s): the snapped value is clamped to the true end, so the window can always end exactly at the source end. Nudges step to the nearest grid line first.
- **Save policy** (`editorStore.setTrim(slot, trim, 'none' | 'debounced' | 'now')`). Pointer drags update the draft on every move but schedule no save; pointerup saves once (`finishTrim`), so one drag = one change (a natural undo boundary for 4.6). Held-key nudges use a 300 ms debounce. Numeric fields commit on blur or Enter and save at once. The debounced callback reads `get().draft` when it FIRES, never a captured recipe (a trim followed by Remove inside 300 ms must not bring the clip back); `commit()` (clip applied, slot cleared) cancels a pending trim save because it already saves the latest draft. `flush()`, `closeDraft()` and `beforeLibrarySwitch()` run a pending trim save first (so `pagehide` is covered, with the same best-effort caveat as #33). `setTrim` is a no-op (no new draft object, no save, no new `inputProps`) when the clamped result equals the current trim.
- **Filmstrip drawing.** The sprite holds `ceil(duration / interval)` frames covering up to a whole interval MORE than the clip, and frames have a natural aspect, so it is not stretched over the track. `filmstripTiles()` cuts the track into cells of a frame's natural width and each cell shows the sprite frame nearest the time under its visible centre (an `<img>` shifted inside a clipped cell, not `background-image`, which the Remotion lint rule forbids).
- **Seeking from the trim UI.** `SeekTarget` gained `{ slot, edge: 'start' | 'end' }` and requests carry `pause`. `PreviewPanel` resolves the edge against a timeline rebuilt from the store's draft at the moment it handles the request (not the one from its last render), so there is no stale-timeline race and the trim UI does no frame math. Trim seeks pause playback first and are throttled to one per animation frame. The last-frame lag from #34 still applies to the right edge preview (one source frame early).
- **Keyboard.** The window and both handles are focusable `role="slider"` elements (values in seconds). Arrows move the window, or the focused edge, 0.1 s (Shift = 1 s). `BracketLeft` moves the start edge earlier, Shift+`[` later; `BracketRight` moves the end edge later, Shift+`]` earlier; always 0.1 s. Matched on `e.code`, not `e.key`, and no Alt: Option+`[` types a different character on macOS and would clash with Shift = 1 s on the arrows.
- **Long clips.** A 3 s window on a 45 s clip is about 20 px wide. Handles have a hit area of 16 px that extends 12 px OUTSIDE the window, and the window body is drawn at least 24 px wide (visual only, the trim is unchanged). A `long_45s.mp4` fixture was added for this.
- **Layout.** The right column is 360 px wide (300 px under 1300 px viewport width) and the left 320 px (280). At the old 1200 px default window width the preview column shrank to about 184 px and the scrubber collapsed to a dot, so: the default window is now 1440x900 with `minWidth` 1100 (was 1200x800 and 900), and the Player controls put the scrubber on its own row.
- **Fixture flash is not a bug.** Every fixture flashes full-frame white for 0.1 s at each whole second (#13, step 0.3), so a paused preview at `t = 1.0 s` of a fixture is white by design. Look at other times when checking previews built from fixtures.

- **Nothing is rendered under the export name.** Like `importClip` (#29), the `render` job builds everything in `cache/tmp/<jobId>/` (`out.mp4`, `out.recipe.json`): render, verify, sidecar. Only then does it pick the name with `buildExportName` (re-reading `exports/<slug>/<date>/` at that moment, not at job start) and put both files into `exports/`. A crash, cancel or failed check leaves nothing in `exports/` and never burns a name; `sweepLibrary` empties `cache/tmp` on the next open. Cleanup of a failed or cancelled job is `rm -r` of its tmp dir.
- **The move never overwrites.** `fs.rename` replaces an existing target on macOS, so files are put in place with `fs.link` (atomic, `EEXIST` if the name is taken) and the source is left for the tmp-dir removal. Filesystems without hard links (`EXDEV`, `EPERM`, `ENOTSUP`: other volumes, exFAT) fall back to `copyFile` with `COPYFILE_EXCL`. A lost race (`EEXIST`) re-picks the name, up to 5 times; if the sidecar cannot be placed the already placed mp4 is removed again, so an mp4 never sits there without its sidecar. The render pool is 1, so a lost race only happens if something else writes into the folder at the same moment.
- **The row and the use counts commit together.** `videos.update(status: exported, export_path, recipe_json)` and one `use_count` increment per distinct `sourceCaptionId` of the recipe run in a single SQLite transaction (`repos.transaction`). A caption used in two slots of one video counts once for that video; a caption deleted from the bank since it was picked is skipped. If that transaction fails, the files just placed in `exports/` are removed and the row is marked `failed`.
- **Exported rows store the corrected recipe.** The name, the sidecar and `recipe_json` all use the product's CURRENT slug (`withProductSlug`, #33). The sidecar is pretty-printed JSON of that recipe.
- **Progress.** Only the `rendering` stage of `renderRecipe` maps to 0-90 % of the job bar; `browser-download` and `bundling` only set the stage label (progress never goes down, so their numbers would pin the bar). Checking is 90-97 %, saving 97-100 %. The Remotion serve URL is created once per session; a rejected attempt is not cached, so the next export retries.
- **Cancel and quit.** `renderRecipe` already deletes its partial output. The runner turns a `cancelled` result into `AbortError` (otherwise the scheduler would record the job as done) and checks the signal once more right before the move; past that point the export is finished, not cancelled. Cancel leaves the row a draft. Quit and library switches use the existing `cancelAll`.
- **Guards while a render is active.** Main tracks `videoId -> jobId`. `videos.saveDraft` and `videos.remove` answer `exporting`, and `videos.export` answers `already-exporting`, while that job is queued or running. In the renderer the draft is frozen from the click on Export until the export panel is left (`exportState` is not `idle`): `commit`, trim, caption text, slot import and clear are ignored, and `startDraft` / `openDraft` / `closeDraft` refuse with a notice while the render is running (the panel only covers the editor, so the New Video page could otherwise close the draft and wipe the export state mid-render). A finished export is closed with `finishExport`, which does NOT save (the row is a video now).
- **`videos.export(recipe)`** validates with zod, upserts the draft (so the row and the render agree), then enqueues. `videos.reveal(id)` resolves the path from the row against the library root in main (the renderer never sends a path) and calls an injected wrapper `(p) => shell.showItemInFolder(p)`; a wrapper rather than the function itself, so an e2e test that replaces `shell.showItemInFolder` at runtime takes effect. The button says "Show in Finder" on macOS and "Show in Explorer" on Windows (`window.api.platform`).
**Revisit if:** exports land on a different volume than `cache/tmp` often enough that the copy fallback matters, or 4.4's render queue needs the tmp-then-move step as a shared helper.

## #38 2026-10-17: Verify severity and failed rows (step 3.5)

- **Hard vs soft.** `verifyRender` (`src/main/render/verify.ts`, shared by the export job and `npm run verify:render`) tags every row. HARD: the output-spec rows from `checkOutputSpec` (size, fps, codec / profile, `yuv420p`, Rec.709 tags, AAC 48 kHz stereo, duration) and faststart. A hard failure deletes the tmp output, marks the row `failed` and shows the failing checks as the error. SOFT: the per-clip audio rows and the colour fidelity row. They are heuristics (one 64 px patch on one frame with a 5/255 limit; volume thresholds) that can false-fail on real handheld clips with motion, so the export still succeeds, the row is `exported`, and the done panel lists the warnings ("Watch the video once before you post it"). A soft check that cannot run at all (unreadable source, ffmpeg error) is also a warning in the app (`catchSoftErrors`), while the script lets it throw as before.
- **The script is unchanged.** It prints the same table and still exits 1 on ANY `FAIL`, hard or soft; only the export job treats soft failures as warnings. Compared with the pre-refactor script on `out/sample.mp4`: identical output and exit code.
- **Failed rows are not dead ends.** A `failed` row would strand the user's work (it could not be re-saved), so a save revives it: `upsertDraft` accepts `draft` and `failed` rows and sets `status = 'draft'`; `videoService.saveDraft` and `remove` treat `failed` like a draft; the editor can open a `failed` row. An `exported` row is still immutable. Cancelling an export does not mark anything failed.
**Revisit if:** soft warnings turn out to be noise (loosen the thresholds) or to hide real problems (promote a check to hard).

## #39 2026-10-18: History, hardening, logs (step 3.6)

- **Exported records are deletable.** DECISIONS #38 said an exported row is immutable; that still holds for SAVING (a draft save never overwrites it) but History needs "delete record", so `videoService.remove` accepts any status. It is still refused while that video's export job is active. The caption `use_count` is NOT decremented when an exported row is deleted: counts are historical ("how often was this caption used in a video I made"), not "how many live videos use it".
- **Delete with files = Trash, in a fixed order.** `remove(id, { deleteFile: true })` on an exported row: (1) the mp4 path is resolved from the row and checked with realpath containment (`resolveInsideReal`) to be inside `<library>/exports/`, otherwise refused (a symlink inside exports/ pointing out is refused too); (2) the mp4 goes to the OS Trash through the injected `trash` wrapper (`shell.trashItem` in `main.ts`, replaced by e2e so tests never touch the real Trash); a file that is already gone (ENOENT or missing) counts as done, any other failure returns an error and keeps the row so the user can retry; (3) then the sidecar, where a failure is only a `warning` in the result; (4) the row is deleted last. "Delete record, keep file" (the default, checkbox off) leaves both files, so the sidecar stays on disk and 4.1's Open Recipe can recover the video. Draft and failed rows ignore `deleteFile`.
- **History data is batched.** One `videos.list()`, one `media.byPaths` for every row's Before clip path, one `videos.exportFiles(ids)` for every exported row; never a call per row. The thumbnail is the media row's own thumbnail (a frame at 10 % of the Before clip, not the trim start); a clip whose row or file is gone shows "No preview". The row's duration is frame-based (`totalSeconds`), like the editor's indicator.
- **A failed `<img>` shows a fallback, never the broken-image icon.** One `Thumb` component with `onError` is used for product photos, b-roll tiles, slot cards, the editor header and History. The media server answers `Cache-Control: private, max-age=3600`, so a thumbnail deleted outside the app can keep rendering from cache for up to an hour; accepted (the clip itself is checked against the disk). A missing filmstrip sprite and a missing b-roll file in the preview modal say so in words.
- **Missing clips are checked in main before a render, and in the renderer for UX.** `exportVideo` stats every clip's `mediaPath` under the library root before rendering and fails with "The before / after / b-roll clip is missing from the library. Replace it and export again." (the draft stays a draft). The editor re-asks `media.byPaths` on window focus, when the already-open draft is opened again from History, and just before Export, so a file deleted mid-session flips the slot to the existing "missing" state; a failed ask is silent.
- **Retry for failed imports is renderer-only.** The editor store keeps the file path of a failed slot import (`retryPaths`, from `PendingImport.filePath`) and `SlotCard` offers "Try again"; `BrollSection` remembers jobId -> path from the `broll.import` result (same order as the input) and the error tile offers "Try again". The jobs tray only gets Dismiss for failed rows (a separate `dismissed` set; the job stays in the store because the b-roll page reads it). Main re-validates every path as before.
- **Load errors are recoverable.** Products, captions, b-roll (page and picker), History and the very first library load show their error with a Try again button; blank-while-loading screens now say "Loading...".
- **Log file.** `<userData>/logs/sandwich.log`, rotated at 2 MB with `sandwich.1.log` and `sandwich.2.log` kept. In userData, not the library, because the library may be in a synced folder. Normal entries go through an async queue (rule 5); only the crash path (`logSync`) and `will-quit` (`flushSync`) write synchronously. `redact()` runs INSIDE the logger on every line, renderer-sent text included, so no call site can leak the media server's per-session token (`/m/<token>` becomes `/m/[token]`). `main.ts` mirrors `console.*` into the log (not in the headless `--render-recipe` / `--db-check` runs), logs failed jobs, `render-process-gone` and `did-fail-load`. Renderer entries (`log.write`) are zod-validated, capped (10 000 + 20 000 characters) and limited to 50 per 10 seconds.
- **Crash handling.** A listener for `uncaughtException` switches off Electron's own crash behaviour, so the handler logs synchronously, shows one `dialog.showErrorBox`, then calls `app.exit(1)`. `unhandledRejection` is logged only. The renderer has an `ErrorBoundary` around `<App/>` (it first tries `editorStore.flush()` so a pending debounced save is not lost, then reports) plus window `error` / `unhandledrejection` listeners; resource load errors do not bubble to the window and are not logged. The crash screen says the work is saved and the draft can be opened from History. Not verified in the packaged app: the `uncaughtException` dialog path (it would end the app; covered by reading the code and the logger's `logSync` test only).
**Revisit if:** the Trash is unavailable on a volume (the delete then fails with a readable message and keeps the record), logs grow noisy from the console mirror, or a thumbnail cached for an hour confuses someone.
